## 0. 反馈解读:三强赢在哪、三冷输在哪

把六张卡带按输入方式和玩法结构对照,共性非常整齐:

| | tilt_maze | busy_knobs | chain_lab | peekaboo | feed_monster | magic_wand |
|---|---|---|---|---|---|---|
| 输入 | 倾斜整机 | 8 实体旋钮 | 摇杆+曲柄 | 捂光传感器 | 隔空手远近 | 隔空手势 |
| 手里有东西可抓? | ✅ 整机 | ✅ 拧 | ✅ 推/摇 | ❌ 对空气 | ❌ 对空气 | ❌ 对空气 |
| 映射维度 | 2D 连续 | 8 路连续 | 2 维(横向+深度) | **1 bit** | 1D(不可见) | 离散分类(还断续) |
| 有决策/技能成长? | 选路、控球越练越稳 | 摆图案 | 选层+对齐 | 无 | 无 | 无 |
| 收集/彩蛋元循环 | 星星+庆祝 | 图案/小鸟/和弦 | 展示架+金星 | 揭晓计数 | 喂 5 个 | 无 |

归因四条(按重要度排序):

1. **实体感是第一位的**。三强的手上都有真实的力/位移反馈:倾斜整机是全身本体感、旋钮有
   阻尼、摇杆曲柄有机械行程。三冷全是"对空气做动作"——捂光、隔空比划——没有触觉回路,
   3~4 岁幼儿得不到"我抓着它、它听我的"的掌控感,而这正是这个年龄段游戏快感的核心。
2. **连续比例映射,信息维度要够**。倾斜多一点球滚快一点、旋钮拧多少柱子长多少——输入量
   与画面量成比例,孩子能"驾驶"。捂/松只有 1 bit(peekaboo v1 试玩结论原话:信息量太低,
   玩一次即弃);手势是离散分类,连"比例"都不存在。
3. **要有随技能成长的真实决策**。迷宫选路会越走越熟、抓娃娃选层对齐是每一把的真决策;
   三冷的动作学会即到顶,新鲜感耗尽就没了。
4. **收集/庆祝/彩蛋元循环放大重复游玩**。星星、展示架、金星、小鸟、图案彩蛋——这些"意外
   之喜"是孩子回头再玩的钩子。三强这层都厚,三冷这层薄或没有。

另外一个交叉证据:magic_wand 的失败**不是执行问题**——传感层标定健康(在场信号占空比
100% 零中断),孩子仍然无感。说明隔空输入这条路是**类型级不匹配**,不是调参能救的。

### 🔴 由此确立的选型铁律(建议回写 CLAUDE.md §10)

> **新卡带的主输入必须同时满足:可抓握(有真实触觉/本体反馈)+ 连续比例映射 + 决策空间
> 随技能成长。** 隔空/环境类传感器(光、超声、手势、PIR)**不再作为主输入立项**,只可作
> 彩蛋级辅助输入(如 busy_knobs 用 IMU 摇一摇洗牌的用法——主输入之外的惊喜层)。

## 5. 2026-08-03:fish_pond 放弃删除(实机试玩后用户拍板)

fish_pond 走完 P1+P2、实机试玩,结论**"还是太简单了"**,代码从仓库删除(git 历史留档)。
**ota_5 空出**。这一节记的不是"又删了一个",而是**它是怎么在满足选型铁律的前提下还是失败的**
——这比 §0 那三冷的教训更值钱,因为那三冷违反铁律、一眼可判,fish_pond **纸面上四条全过**。

### 事后诊断:主输入在玩法上没有功能

对照 §0 归因四条:①实体感(Chain 摇杆+曲柄,可抓握)✅ ②连续比例映射 ✅ ④收集/庆祝元循环
(木桶集 3 + 放生派对)✅ ③**随技能成长的真实决策——纸面成立、实现落空**。

根因在 `fish.c` 的 `AI_CHASE`:**鱼主动游向饵的 x**。

```c
float dx = bx - f->x;                       // 鱼朝饵靠过来
if (fabsf(dx) > step) f->x += (dx > 0 ? 1 : -1) * step;
```

连锁后果:

- 鱼巡游 15~25 px/s、来回一趟 ~8s,**船停在哪都行**,鱼迟早自己游过来;进 `SENSE_R=80` 还
  加速 1.5 倍扑上来,`BITE_R=30` 判定又宽容。
- 于是**摇杆(整个游戏的实体感主输入)在玩法上没有功能**,操作退化成"曲柄把饵放到那条鱼的
  水深(±30px),等,收线"。SPEC §0-3 押的新技能轴("把饵埋伏到鱼的行进路径前方")
  **在实现里根本不存在**——鱼替玩家完成了瞄准。3 岁和 4 岁玩到的是同一个游戏。
- `REEL_LAZY_RATIO=0.5` 让大懒鱼要摇两倍圈数,但两条鱼进桶都只算 1 → **纯成本零收益**,
  "选鱼决策"不是决策,理性选择永远是浅层胖鱼。

### 更结构性的一条:每张卡带必须有一条**非技能**的深度轴

三强的耐玩深度其实都不在技能轴上:

| | 深度来自 |
|---|---|
| tilt_maze | **内容轴**:16×12 手工编排关卡 + BFS 校验,一关一个样 |
| busy_knobs | **表达轴**:8 路旋钮的组合空间,孩子自己发明玩法 |
| chain_lab | **空间变化轴**:每把奖品分布不同 + 展示架收集 |
| fish_pond | ❌ 无内容轴(2 条鱼、固定泳道)、无表达轴(1 个饵 1 个动作) |

fish_pond **把全部赌注押在技能轴上,然后把技能轴写没了**,于是归零。

### 🔴 回写选型铁律(补 §0 那条的第二半)

> 立项时除了"可抓握 + 连续比例映射 + 决策空间"之外,还要过两道**实现级**验收:
>
> 1. **主输入功能性检验**:把每个主输入分别"钉死"做思想实验——**钉死后游戏还能通关吗?**
>    能,那个输入就是装饰。fish_pond 钉死摇杆照样能钓到鱼 → 摇杆是装饰。**这道题在写
>    SPEC 时就能做,不必等实机。**
> 2. **非技能深度轴**:内容 / 表达 / 空间变化,至少要有一条。只靠"动作越练越准"撑不住
>    重复游玩——零失败 + 无计时的设计前提已经拿掉了紧张感这条轴,剩下的必须补上。
>
> 另:**AI 追玩家 = 帮玩家瞄准 = 抹掉技能轴**。宽容判定(大 `BITE_R`)是对的(零失败),
> 但宽容应该体现在"没打中也不惩罚",不是"不用打中"。

## 6. 2026-08-06:ota_3 立项 clock_turn 转转钟(**平台第一张教育卡带**)

用户拍板方向:**突破游戏设定,单纯教育目的**。施工图 `apps/clock_turn/SPEC.md`。

**它与前面所有卡带的根本差别**:目标不是"好玩到反复玩",而是"教会一件具体的事"——
口语时间 ↔ 表盘几何的互译。因此本文 §0/§5 那套**为游戏立的选型铁律,对它部分豁免**
(零失败的表现形式、内容轴厚度当立项门槛、即拿即玩不能有教程、必须独自可玩),
豁免清单与仍然生效的硬约束逐条写在 SPEC §0.2。**别拿游戏卡带的验收标准去卡它。**

仍然过了的两道实现级验收(§5 铁律):

1. **主输入功能性检验** ✅ 钉死 Chain Encoder → 指针完全不动 → 两个模式全瘫。
   结构上不可能出现 fish_pond 那种"AI 替玩家瞄准",因为指针没有任何自己动的路径。
2. **非技能深度轴** —— 教育应用不适用(重复即巩固),已按 SPEC §0.2 显式豁免。

关键设计决策留档(推导见 SPEC):**单旋钮联动而非双旋钮各控一针**(双旋钮能造出现实中
不存在的钟面 = 教错);**1 格 = 5 分钟**(编码器 24 格/圈的硬事实推出);**时针必须 2.5°/步
连续爬行不许吸附**(否则 7:30 的时针跳回 7,把最核心的知识点教反)。

### 🔴 由本卡带确立的教育设计原则:不许教出目标环境里不存在的线索

用户 2026-08-06 否掉了初版的"时针红、分针蓝",理由值得升格为**所有教育卡带的通用原则**:

> **真实钟表的两根针是同一个颜色。** 孩子若在应用里学会靠红蓝认针,回到家里的挂钟前
> 就不会读了 —— 我们教出了一条**目标环境里根本不存在的线索**。

这类错误叫**迁移失败**(transfer failure),它的危险在于**在本机上永远不会暴露**:应用里
一切正常、孩子答得又快又对,只在面对真实物体时才失效,而那正是全部教学目的所在。

由此立一条**教育卡带专属的验收题**(与 §5 那两道实现级验收并列):

> **辅助线索检验**:把画面里每一条帮助孩子做出判断的线索列出来,逐条问——
> **这条线索在真实世界的那个东西上存在吗?** 不存在的,要么删掉,要么确保它只是
> 冗余的第二通道、拿掉后任务仍然可完成。
>
> clock_turn 的落地:两针同色,区分只靠长短(时针 42 : 分针 72)+ 粗细(8 : 5);为解决
> 6:30 这类两针近重叠的时刻,给指针描一圈钟面色的边 —— **真表用金属边框做同一件事**,
> 所以合规。

游戏卡带不受这条约束(游戏里的颜色编码是自洽的设计语言,不需要向外迁移)。

### 🔴 2026-08-06 同日推翻:语音播报整章作废,改双模式

初版给本卡带排了 ~30 条语音、`storage` 分区(0xD90000,2.5MB SPIFFS)当资产区、外加
`voice_gen.py`/`voice_pack.sh` 一套平台级新增基础设施。**全部取消**,理由是一句朴素的观察:

> 录音只会说「七点半」一种说法,而大人嘴里能出「七点三十」「差一刻八点」「七点过一点点」,
> 还能追问、换说法再来一次。**大人本人就是更好的语音引擎。**

附带的两条:固定语音重复几百遍,**先受不了的是大人**;而反馈用的"好棒/再试一下"这类话,
在有大人陪的场景里由真人说本就更好,独自玩时 `audio_fx` 的程序化音效 + 灯带 + 震动也够。

代之以两个显式模式(详见 SPEC §2):**MODE_FREE** 大人口头出题、孩子拨、按旋钮键揭晓数字
当客观裁判;**MODE_QUIZ** 屏上显示目标时刻、孩子拨、按键判定 + 渐进提示弧。

**平台级后果**:`storage` 分区**至今仍无使用者**(留给以后真正需要大对象素材的卡带);
clock_turn 是零外部资产的纯代码卡带。**教训**:立项时最容易高估的就是"要不要自建一套
基础设施"——先问一遍这件事**能不能由在场的人做得更好**,能,就别写代码。

### 🔴 用户的否决理由(两条,以此为准)

> 「图形太多太复杂,无法玩出什么花样」

**一、一屏上的对象太多、太杂。** 数一下同屏元素:天空 + 云 + 太阳 + 水龙头 + 3 段管 + 管箍
+ 石头 + 3 个花盆花 + 出口管 + 水洼 + 芦苇。**每个对象单独看都合规**(§8 的 ≥64px 全过),
但**加起来对 3~4 岁就是一屏噪声**。对比三强:tilt_maze 是一个球 + 一堵墙,busy_knobs 是
8 个格子,chick_pour 是一群鸡 + 一个窝——**画面上「要看的东西」都只有一两类**。

> 🔴 **平台补一条规矩:§8 只约束了单个对象够不够大,没约束一屏能放几类。**
> 大对象护眼线拦得住「太小」,拦不住「太挤」——而幼儿卡带死在「太挤」上更容易。
> 新卡带的画面自检加一问:**孩子需要同时盯住几类东西?超过两类就要砍。**

**二、玩不出花样。** 这是更致命的一条,而且**§5 那条铁律本该拦住它**:每张卡带必须有一条
**非技能的深度轴**。pipe_garden 的操作从头到尾只有一个——「拧到管口对齐」。换关只是换石头
位置,操作完全同构,**没有任何新东西在后面等着**。SPEC §0.3 用「空间规划新轴」这个说法
把这一点糊过去了:空间规划是**技能轴**(玩久了更会看路),不是内容轴。
**「换布局」不等于「有花样」**——布局变了但玩法动作一模一样,孩子第三关就知道后面全一样。

### 效果图顺带暴露的三处 SPEC 级缺陷(不是否决理由,但值得留档)

## 8. 2026-08-12:省电批(DEEP 不是终点站)

**起因**:日常使用"放一阵就彻底没电了",现场看屏和灯带明明都灭了。

**根因**:三级省电机制本身对、六个工程也全接上了,但它省的是**外设电**(屏 / 灯带 / M-Bus 5V),
**从没碰过主控侧**;而且 DEEP 是终点站——设备永远不会自己关机,只会一直跑到电池放空
(500mAh 电芯还每次都是深放电)。"屏和灯带都灭了却还是耗干",灭掉的正是唯一看得见的那部分。

**已做**(实现细节在 `components/core2_sleep/README.md` 与 `power_monitor/README.md`,不在此重复):
DEEP 满 10min 自动关机 + 任何阶段电压 <3300mV 关机(插着 USB 两条都跳过);tilt_maze 的
ATTRACT 补进可打盹态、三处 `&& have` 去掉;launcher 与 tilt_maze 的 `LV_ANIM_REPEAT_INFINITE`
接上 `on_stage_change` 在休眠时删掉;新增 `power_monitor` 组件 + launcher/clock_turn 的电量指示。

### 🔴 仍未做的:主控侧一行都没动

当前配置(已核实 `launcher/sdkconfig`):`# CONFIG_PM_ENABLE is not set`、无 tickless idle、
CPU 固定 160MHz、`CONFIG_FREERTOS_HZ=1000`、`CONFIG_SPIRAM=y` 全套且从不断电。

⚠️ 一个容易说过头的地方:**没开 PM 不等于"CPU 满负荷空转"**。
**Confirmed via IDF v6.0 `components/esp_system/freertos_hooks.c`**:没开 PM 时 idle 钩子走
`esp_cpu_wait_for_intr()`(WAITI),核在中断间隙是停的。真正没省的是 **PLL/APB 时钟常开、
外设常时钟、PSRAM 与 flash 常供电,外加 tick 1000Hz 让内核每 1ms 就被叫醒一次**(DEEP 里
我们自己那 8Hz 轮询反倒是小头)。这个区别直接决定下一步该动谁。

| 做法 | 代价 / 风险 |
|---|---|
| `FREERTOS_HZ` 1000→100 | 最便宜(一行),但全仓 `pdMS_TO_TICKS(16)` 的 60fps 节奏会变 10ms 粒度,手感要实测 |
| DFS(`PM_ENABLE` + `esp_pm_configure`,idle 降到 XTAL 40MHz) | 与 PSRAM **不冲突**(官方有 `mspi_psram_with_dfs` 测试用例);代价是中断延迟最大 +40µs、RTOS 计时精度下降 → SPI 刷屏与 I2S 音频要验 |
| 自动 light sleep | 省最多,但外设被时钟门控、GPIO 中断不发,要显式配唤醒源;且 🔴 **开着 PSRAM 就不能 `ESP_SLEEP_POWER_DOWN_FLASH`**(flash 与 PSRAM 共用电源脚,断了丢数据)→ 带 PSRAM 的 light sleep 电流下不到手册那个数。这正是当初避开它的原因之一 |
| 关掉 PSRAM | 自家代码只有 `components/screenshot/screenshot.c` 两处 `MALLOC_CAP_SPIRAM`(150KB 帧 + 230KB RLE)——**关掉 = 失去截图自查**(CLAUDE.md §10.1 那条 AI 看屏的路);且 `SPIRAM_USE_MALLOC=y`,BSP/LVGL 的大块分配现在也可能落在 PSRAM,得先确认内部 RAM 兜得住 |

另有三处外设侧的余量没动:DEEP 里没断 LDO2(屏逻辑电)、没关 NS4168 功放(§5.1 防爆音纪律的
代价)、`ledstrip` task 在 5V 已切时仍无条件 `led_strip_refresh()`。

### 下一步先量什么

**别按上表的顺序动手**。自动关机已经把"待机"这一段的收益按到零了,DFS / light sleep 真正
值钱的地方其实是**正在玩的时候**——那才是续航大头。所以要量的是"玩着的时候多少 mA",
不是待机。🔴 **插着 USB 量不到任何真数**(VBUS 在位时系统吃 USB 的电、电池转充电,
放电电流恒 ~0),实用测法见 `components/core2_sleep/README.md` 末节。
